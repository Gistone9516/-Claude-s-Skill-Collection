## Work recovery
How to handle errors/corruption during file edits. **File-recovery methods are common to all projects, so accumulate them here.**

### Automation robustness — ★STRONG RULE (a format error that halts the run = critical defect)
A single malformed tool-call or an unguarded script crash aborts the whole automation. In long multi-step / agent-orchestrated work this is unacceptable. Enforce:
- **No complex inline shell.** Multi-line commands, or anything with quotes / special chars / Korean / heredocs (esp. `python -c "..."`), routinely break tool-call parsing (malformed → the entire call fails, run stalls). → **Write a `.py`/`.sh` file then execute it.** Inline only for genuinely simple one-liners (`ls`, `cp a b`). This was the actual cause of repeated mid-run halts — verbatim Korean+quotes in `python -c`.
- **Every automation script wraps its logic in try/except (or equivalent).** Catch per stage, **print which stage failed and why** (no silent death / ambiguous stall). Validate inputs exist up front; validate the output artifact at the end and **delete the partial file on failure** so a broken artifact never looks done. A partial-stage failure must not silently poison the pipeline.
- **One tool call at a time, format verified** — check block closure and parameter shape before sending. One malformed call halts the whole automation; treat tool-call hygiene as load-bearing.
- **★ Response-truncation → malformed call (the #1 silent-halt in long sessions).** The real cause is **total output volume per response**, NOT Write/tools themselves (Write & Workflow are essential to automation — don't suppress them). What stalls: one response packing **long prose + a long tool payload** hits the output ceiling → tool block cut mid-way → unclosed = nothing runs = silent stall (renders as plain text). Manage volume, don't avoid tools:
  - **Never put long prose and a long payload in the same response.** A long payload (big Write, Workflow `.js` script, multi-line command) goes **alone, with near-zero prose**.
  - **At most ONE long payload per response.**
  - Prefer a targeted **Edit** over a full re-Write when changing a few lines (smaller payload), but Writing a long new script is fine when it's the response's only content.
  - **Do NOT skip accuracy-critical steps** (e.g. canonical re-extraction in deepflow-auto) — only pure diagnostic/summary aux is skippable.
  - Symptom check: if a tool call renders as plain text with no result, it was truncated → resend it **alone, shortened**.
- **Idempotent & resumable** where possible — re-running shouldn't corrupt prior output; Workflow runs carry `resumeFromRunId`.

### Document text extraction (docx·xlsx·hwpx·pptx → text, ★default)
- **Extraction output always to a UTF-8 file.** This environment is Korean-file-heavy but the Windows console is cp949, so printing python extraction straight to stdout throws `UnicodeEncodeError` on Korean/special chars (e.g. `\xa9` ©) and breaks the whole extraction. So write the result to a UTF-8 file via `open(path,"w",encoding="utf-8").write(...)` **then Read it with the Read tool**. No direct console print.

### HWPX editing (★read this before ANY hwpx work)
- **Rule 0 — remove ALL linesegarray (overwhelming #1 cause of corruption errors).** If you change even one character of text, **remove every `<hp:linesegarray>` from the entire section XML** that text belongs to. Otherwise Hancom rejects it as "document is corrupted, won't open" (the recurring #1 trap). Removing only "the edited paragraph" is insufficient — missing a body paragraph leaves it corrupt.
  - String replace: `re.sub(r"<hp:linesegarray>.*?</hp:linesegarray>","",d,flags=re.S)` + also remove self-closing `<hp:linesegarray/>` → confirm XML parses OK after removal.
  - lxml: live-tree immediate removal skips siblings, so **materialize the list first, then delete**.
  - Why: linesegarray is a geometry cache of line/char positions. When `<hp:t>` length changes the cache indices go out of bounds → "corrupt" verdict. Hancom recomputes on open, so removal is lossless.
- **Rule 1 — drop hashkey when replacing an embedded image.** The `hashkey="..."` (Hancom's proprietary hash) integrity value on the `<opf:item>` in `Contents/content.hpf` mismatches the replaced bytes → "corrupt". **Delete the replaced image's `hashkey` attribute entirely** → the check is skipped and it opens. Match the replacement image to the original's exact pixel dimensions to keep frame/distortion unchanged.
- **Rule 2 — no CJK regex char-class.** A range like `[一-鿿…]` can, on a boundary error, match Hangul (AC00–D7A3) and delete body text. Do CJK matching/replacement with **literal str.find/replace only**, and verify `count == expected` before replacing.
- **Rule 3 — repackaging.** Copy the original zip and **replace only changed entries** (preserve other bytes, order, compress_type). `mimetype` = first entry, STORED (`application/hwp+zip`). Body XML has no BOM, no CR/LF.
- **Rule 4 — pre-delivery validation.** ① all section/hpf XML parse OK ② linesegarray residue = 0 ③ mimetype first & STORED ④ zip testzip None ⑤ unedited `<hp:t>` identical to original ⑥ changed-entry count matches intent.

### PPTX editing
- **"Do you want to repair?" is a warning, not an error.** Ignore it; click "repair"/"yes" and the file opens fine. Don't misread this as "won't open" and waste effort. Font-embedded decks can show this prompt from the original itself — if suspected, **byte-diff against the original** first to confirm "not my edit's fault."
- **Common cause = `<Default xmlns="" .../>` in `[Content_Types].xml`.** `xmlns=""` pulls Default out of the OPC namespace → schema violation → repair trigger. Removing just `xmlns=""` cleans it while keeping font embedding (removal optional).
- **Diagnostic oracle = .NET `System.IO.Packaging.Package.Open` (Add-Type WindowsBase).** PowerPoint COM unconditionally fails even on healthy files in this environment (automation blocked) so it's useless; python-pptx/zipfile/minidom are too lenient and pass broken files. Trust only .NET OPC for the OPC layer (it doesn't check slide PresentationML schema, though).
- **python-pptx round-trips drop embedded fonts (.fntdata)** and break the deck → use manual ZIP/XML injection or a new file only. Recompress to the original compress_type profile (STORED if STORED), and build a fresh `ZipInfo` preserving external_attr & date_time.
- When removing a slide, remove both the sldIdLst entry in `presentation.xml` and the rId in `presentation.xml.rels` (else dangling). Overwriting existing + adding only the shortfall is lower-risk than removal.
- **Diagnostic principle (general): change one variable at a time to isolate.** Changing several at once can't narrow the cause.

## Writing style (Korean deliverables)
- **No AI-sounding writing (all prose).** Human-read deliverables (자소서/cover letter, 회의록/minutes, papers, reports) must not read as AI-written. Avoid needless jargon/buzzword-stacking, 한자 (Sino-Korean) glosses, and excessive modifiers; write naturally, centered on real experience/content. (Per-deliverable format & ending-tone: see that project's memory.)
- **Provided text is verbatim — never transform/summarize/paraphrase.** Narrative text a teammate/user wrote themselves is used **exactly, not one character changed**. No summarizing, paraphrasing, ending-change, word-swap (arbitrarily altering agreed wording damages it). Only line-break positions may be adjusted to fit layout. Don't mix my draft with the provided source; mark my parts as "my draft." If unclear, ask via AskUserQuestion before output.
- **Presentation slides = minimal.** Don't write full sentences — keep **only key keywords/numbers** (the presenter speaks the rest; fully-written slides are boring). Style = 개조식 음슴체 (telegraphic, noun-form / ~ㅁ / ~함 endings); ban "~입니다/~한다" forms. Card pattern = subhead (noun phrase) + 2–3 short fragments. No 한자 (必→필요); abbreviations/numbers OK. Write long only when "for evidence/support" is explicitly requested, still in 음슴체.
